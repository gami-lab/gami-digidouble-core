## Executive Summary

Most of the EPIC was delivered and the hack removal is real. The dead `session_memories` /
`avatar_session_memories` mirrors are gone end to end: tables, ports, repositories, wiring, reset
paths, and admin fields. Covered-topics read defaults, the evaluator's `'legacy'` provider and old
report fields, all three stale TODOs, and several excuse-comment swallowed errors were removed or
replaced with bounded warnings. Redis idempotency records no longer grow without bound. Comment
volume dropped from 1,553 to about 1,175 comment-bearing lines with no lint, type, or test
regression, and a comment-policy lint rule now runs in `pnpm lint` and the pre-commit hook.

Three weaknesses keep this from a clean close:

1. **The unlock-state fix (H4) is incomplete and leaves conflicting meanings.** The shared DTO and
   the database now require `unlockedAvatarIds`, but the domain `Session` type still has it
   optional. `avatar-awareness.service.ts` still reads `undefined` as "every Avatar available",
   while `GetAvailableAvatarsUseCase`, `SwitchAvatarUseCase`, and GM unlock routing now read it as
   "none available".
2. **Suppression removal mostly didn't happen.** `eslint-disable` went from 169 to 161
   directives. Of the 73 outside tests, 42 share the same generic reason ("retained non-linear
   boundary mapping is clearer together"), and six production files keep a file-level
   `max-lines` disable. The rule now requires a reason, but these reasons don't explain anything
   specific.
3. **The new behaviors are not proven by tests.** No test covers "a scenario with no
   unlock policy starts the session with every active Avatar unlocked" (the old test was deleted
   and not replaced). The Redis TTL behavior runs against a no-op `pexpire` stub, so nothing
   asserts it.

The guardrail also has precision problems: it flags legitimate provider-quirk comments that
mention Claude and comments like "generated by PostgreSQL", misses common narration phrasing, and
accepts any text after `--` as a reason.

## Final Grade

**C — acceptable but meaningful weaknesses.**

The build is green and the dead-code removal is high quality. An A is ruled out by contract
optionality drift on `Session.unlockedAvatarIds` across the domain, shared, and persistence layers,
and by behavior changes that no test proves. A B is not justified because the EPIC's central
hardening goal for suppressions (remove the hack, don't just annotate it) was mostly replaced with
boilerplate reasons, and the guardrail is not precise enough to trust as a long-term enforcer.

## Findings

### Unlock-state optionality drift and conflicting `undefined` meanings

- Severity: High
- Category: contract drift / correctness
- Problem: `SessionSummary.unlockedAvatarIds` (shared) and `sessions.unlocked_avatar_ids`
  (schema) are now required, but `domain/conversation/session.types.ts:8` and
  `domain/game-master/game-master.types.ts:150` keep the field optional.
  `domain/avatar/avatar-awareness.service.ts:7,16` still treats `undefined` as "every Avatar
  available", while `get-available-avatars.use-case.ts`, `switch-avatar.use-case.ts`, and
  `run-game-master.avatar-unlocks.ts` now treat it as locked (`?.includes(...) === true`,
  `?? []`).
- Why it matters: this is the exact hack H4 was meant to remove. Postgres always returns an array
  now, so the `undefined` branches are dead in production but live in in-memory tests and
  fixtures. The Avatar prompt and the availability API can disagree about which Avatars exist, and
  the optional type invites someone to rely on `undefined` again.
- Evidence: the files above; `git show 4190d91c` replaced the `undefined` checks with optional
  chaining instead of tightening the type.
- Recommendation: make `Session.unlockedAvatarIds: string[]` required in the domain and GM types,
  remove the `undefined` parameter and branch from `buildAvatarAwareness`, and delete the
  `?.` / `?? []` guards.

### No test proves the new unlock behavior

- Severity: High
- Category: test coverage
- Problem: `resolveInitialUnlockedAvatarIds` now returns every active Avatar when the scenario has
  no policy. No test asserts it: `start-session.use-case.test.ts` only added
  `unlockedAvatarIds: []` to fixtures, and the 41-line "sessions without unlock state" test in
  `get-available-avatars.use-case.test.ts` was deleted without a replacement.
- Why it matters: this is a behavior change that operators will notice. Before, "no policy" meant
  live access to every active Avatar. Now it is a snapshot taken at session start, so Avatars added
  or activated later stay locked for existing sessions. Prompt `02` explicitly required replacing
  legacy tests with tests of the new invariant.
- Evidence: `grep resolveInitialUnlockedAvatarIds` in tests returns nothing.
- Recommendation: add a domain test (no policy returns active IDs, inactive Avatars excluded) and a
  start-session test that persists them. Record the snapshot behavior in `API_CONTRACT.md`, or
  decide it should stay dynamic.

### Suppression removal replaced by boilerplate reasons

- Severity: Medium
- Category: maintainability / EPIC scope
- Problem: 161 `eslint-disable` directives remain (169 at baseline). Of 73 outside tests, 42 say
  "retained non-linear boundary mapping is clearer together", 12 "retained fixture or
  orchestration setup is clearer together", and 6 are file-level `max-lines` keeps
  (`send-message.use-case.ts`, `list-session-events.use-case.ts`,
  `knowledge-ingestion.service.ts`, `postgres-knowledge-corpus.repository.ts`,
  `context-engine.service.ts`, `viewer-page.ts`).
- Why it matters: prompt `03` asked for refactoring, with keeps only where splitting would make the
  code worse and a specific reason for each. A reason copied onto 42 functions documents nothing.
  The core turn orchestrator (`send-message.use-case.ts`) remains over the file-size limit.
- Evidence: `grep -rn eslint-disable apps packages tools | grep -oE -- '-- .*' | sort | uniq -c`.
- Recommendation: treat this as a follow-up slice. Split the six file-level keeps first, then the
  `complexity` keeps in production code, and replace each surviving reason with one that names the
  specific construct (e.g. "exhaustive switch over `ProviderErrorKind`").

### Guardrail false positives, false negatives, and a reason check any text passes

- Severity: Medium
- Category: tooling quality
- Problem: probing the rule directly:
  - flags `// Claude models reject temperature above 1, so clamp it.` (a legitimate provider quirk
    in a codebase with an Anthropic adapter)
  - flags `// IDs are generated by PostgreSQL, never by the client.`
  - flags `// Fixed-size window keeps the prompt bounded.` and `// Now() is evaluated by the database…`
  - misses `// This function was rewritten to use the new port.`, `/* AI-generated helper */`, and
    `// Handle the null case that broke after the refactor.`
  - `ESLINT_REASON = /--\s+\S/` accepts `-- x`.
- Why it matters: false positives push authors to reword or delete useful "why" comments, which is
  the opposite of the policy. False negatives let the most common narration through. The
  boilerplate-reason finding above shows the reason check is already being satisfied mechanically.
- Evidence: `eslint-rules/no-agent-comments.mjs`; the RuleTester suite has only 4 valid and 4
  invalid cases.
- Recommendation: narrow `AI_ATTRIBUTION` to attribution phrasing (`(generated|written|added) by
(ai|claude|copilot|codex|an? (llm|agent))`, `ai-generated`). Only treat `fixed`/`now` as
  narration when followed by a verb-like pattern, or drop them. Add rewritten/refactored/after-the
  patterns. Require a minimum reason length. Add each probe above as a RuleTester case.

### Redis TTL behavior is untested and not atomic

- Severity: Low
- Category: correctness / test coverage
- Problem: `reserve` does `SET key value NX` and then a separate `PEXPIRE`; `complete` does
  `SET XX` then `PEXPIRE`. The test double's `pexpire` returns without recording anything.
- Why it matters: a process crash between the two calls leaves a key with no TTL, which is the
  unbounded-growth problem H10 was meant to fix. No test would catch a regression in retention.
- Evidence: `redis-utterance-idempotency.store.ts:63-67,86`; `redis-utterance-idempotency.store.test.ts:20`.
- Recommendation: use `SET key value NX PX <ttl>` and `SET key value XX PX <retention>` in one
  call, and make the fake record TTLs so tests assert both values.

### Comment sweep was conservative in Core application code

- Severity: Low
- Category: EPIC scope
- Problem: Core application comments went from 250 to 223 lines and API from 50 to 47, while
  domain dropped from 215 to 130. Much of what remains is suppression reasons.
- Why it matters: application code holds the orchestration and is read most often by agents. The
  numbers suggest the stricter "good code shouldn't need comments" stance was applied unevenly.
- Evidence: `COMMENT_INVENTORY.md`, Core prompt 04 before/after table.
- Recommendation: re-sweep `apps/core/src/application` after the suppression refactor, since many
  remaining lines are disable directives.

## Architecture Review

Boundaries are respected. Removing the mirror repositories simplified `composition.ts`,
`server.ts`, `index.ts`, and four route modules without moving logic across layers. Error handling
now propagates typed failures instead of hiding them. The new `toJsonValue` boundary stays in
Infrastructure. No new dependency, datastore, or endpoint was added. The one piece of drift is the
`unlockedAvatarIds` optionality split between the Domain (optional) and the shared contract and
persistence (required).

## Test Review

- **Strong tests:** schema-contract integration test asserting the removed tables are absent;
  corpus-bootstrap rejection now propagating (`knowledge-ingestion.service.test.ts:698`); typed
  retrieval and knowledge-chunk integration tests rewritten to insert fixtures directly instead of
  through a production fixture-only method; RuleTester suite run by `pnpm test`.
- **Weak tests:** `redis-utterance-idempotency.store.test.ts` covers state transitions but uses a
  no-op `pexpire`, so retention is unproven.
- **Missing tests:**
  - a scenario with no policy unlocks every active Avatar at session start
  - avatar awareness and available Avatars agree for the same session
  - a malformed persisted `covered_topics` array fails the read
  - bounded warning emission for hydration and reservation-cleanup failures
  - false-positive and false-negative cases for the comment rule
- **Implementation-coupled tests:** none newly introduced. Deleted legacy tests were coupled to
  removed behavior and were correctly removed, but two of them were not replaced with tests of the
  new invariant.

## Documentation Gaps

- `API_CONTRACT.md` says an empty `unlockedAvatarIds` means no Avatar is unlocked, but doesn't say
  that a scenario with no policy gets every active Avatar unlocked at session start, or that later
  scenario changes don't reach existing sessions.
- `EPICS.md` and `PROJECT_STATUS.md` say the EPIC refactored unexplained production suppressions.
  In practice they were mostly annotated, not refactored; the remaining suppression debt should be
  stated as a follow-up.
- `TEST_COVERAGE_PLAN.md` should list the missing unlock and Redis TTL tests until they are added.

## Path to A

1. Make `Session.unlockedAvatarIds` required in the domain and GM types; remove the `undefined`
   branch from `buildAvatarAwareness` and the `?.` / `?? []` guards.
2. Add the no-policy unlock tests and a consistency test between awareness and available Avatars;
   document the snapshot behavior in `API_CONTRACT.md`.
3. Use atomic `SET … PX` in the Redis idempotency store and assert TTLs in its tests.
4. Fix the comment rule's patterns and reason length, and add the probe cases to RuleTester.
5. Split the six production file-level `max-lines` keeps and replace boilerplate reasons with
   specific ones (or open a dedicated follow-up EPIC for this and record it in `EPICS.md`).

Steps 1–4 are small; step 5 is the larger piece.

## Final Recommendation

**Close with debt.** The hack removal and dead-code deletion are solid and the build is green, so
there's no reason to roll anything back. Fix the unlock-state drift and add its tests (steps 1–2)
before building on session availability. Track the suppression refactor and guardrail precision
(steps 3–5) as an explicit follow-up rather than leaving the EPIC marked as having refactored them.
